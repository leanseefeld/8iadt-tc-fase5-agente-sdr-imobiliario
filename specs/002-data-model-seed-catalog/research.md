# Phase 0 Research: Data Model, Seed and Catalog

No `[NEEDS CLARIFICATION]` markers remained in the spec — the five self-clarify questions there cover the choices that had more than one reasonable answer. This file records the narrower implementation-level decisions the plan depends on.

## Migration mechanism

**Decision**: a one-shot `migrate` Compose service (`command: node src/db/migrate.ts`), using `drizzle-orm/node-postgres/migrator`'s `migrate()` against the migrations folder. `app` and `worker` depend on it via `condition: service_completed_successfully`.

**Rationale**: exactly one process ever runs the migrator, so there is no advisory-lock race to get right, and no lock code to test. Compose already expresses "wait for X to finish, then start" natively — the same primitive `service_healthy` uses for the database wait in spec 001. This is strictly less code than migrate-on-boot with `pg_advisory_lock`, which would need retry/backoff logic for the loser of the lock race and a way to distinguish "someone else is migrating" from "migration is stuck."

**Alternatives considered**: migrate-on-boot in `app`'s own entrypoint, guarded by `pg_advisory_lock`. Rejected — two processes (`app`, `worker`) would both attempt it, and the loser needs to poll until the winner finishes, which is exactly the readiness-check logic this plan already needs for a different reason (FR-006). Building it twice, once as a startup gate and once as a readiness probe, is worse than building the readiness probe alone and keeping migration ownership in a single dedicated container.

## Readiness `migrations` check

**Decision**: read expected migration tags from `src/db/migrations/meta/_journal.json` (drizzle-kit's own manifest, already committed), compare against rows applied in drizzle's migrations-tracking table.

**Rationale**: no second source of truth to keep in sync — the journal is regenerated by `drizzle-kit generate` in the same commit as the migration itself. Comparing against a hand-maintained constant (e.g., "expect 3 migrations") would drift the first time someone forgets to bump it.

**Alternatives considered**: checking for the mere existence of a few "known" tables (e.g., `agencies`). Rejected — it would report ready after a partial migration that created early tables but failed on a later one, which is precisely the half-migrated state FR-006 exists to catch.

## `searchProperties` ranking and relaxation

**Decision**: a pure function in `domain/property-ranking.ts` over an already-fetched candidate list. Ranking key: `(|price - priceMax|, neighborhoodMatch ? 0 : 1, id)`, ascending. Relaxation ladder, evaluated against the full active+`transaction`-matching set at each step until one is non-empty: (1) `neighborhood ∈ criteria.neighborhoods` (skipped if the list is empty — "open to suggestions"), (2) `region ∈ regionsOf(criteria.neighborhoods)`, (3) no location filter, (4) no location filter and `price ≤ priceMax × 1.2` (the constant `PRICE_RELAX_FACTOR = 1.2`, named so a future spec can tune it without touching logic). `bedrooms ≥ criteria.bedrooms` is never relaxed — spec FR-019 lists only neighborhood/region/location/price in the ladder, and dropping the bedroom floor would return a wrong-sized property, which is worse for the pitch than returning fewer results.

**Rationale**: pure function means spec 004's tool call is exercised in tests with zero database or model dependency, matching the constitution's "domain imports nothing" boundary and giving spec 004 a seam it can trust without re-deriving the ranking itself. Concretely, that boundary means `property-ranking.ts` cannot import the `Property` type `services/properties.ts` returns (that would be `domain/` importing outward, which the ESLint `isolatedDomain` zone forbids) — it declares its own minimal candidate shape (`id`, `price`, `neighborhood`, `region`), and `services/properties.ts` maps down to it and back up, keeping the full entity shape a `services/`-only concern.

**Consequence documented for honesty**: because bedrooms is never relaxed, a criteria combination whose bedroom minimum no property in the agency satisfies will legitimately return zero results even when other active properties exist. SC-005's "zero only when the agency has no active properties" holds against the seeded 100-row dataset, which is deliberately built to cover a wide bedroom range per zone (FR-011) — it is a property of the seed data, not a mathematical guarantee of the ranking function for arbitrary inputs.

## Seed idempotency strategy

**Decision**: natural-key upserts for agency/users/properties (`slug`, (`agencyId`,`email`), (`agencyId`,`code`)); existence-check-and-skip for the three demo leads, keyed by (`agencyId`,`channel`,`externalId` = `seed-hot`/`seed-warm`/`seed-cold`).

**Rationale**: a lead's conversation, messages and events have no natural key to upsert against — "the third message in lead X's transcript" is not addressable content, only a position. Re-running the seed is meant to be safe, not to re-synchronize a demo transcript that nothing else in the system rewrites. Users get `ON CONFLICT DO NOTHING` rather than `DO UPDATE`, because re-hashing an unchanged `demo1234` on every run is pure cost with no observable benefit; properties get `DO UPDATE` because the dataset (owned by a separate process) may legitimately change between runs and the seed should reflect that.

**Alternatives considered**: `TRUNCATE` and re-insert every run. Rejected — it would also delete any runtime data a later spec's demo has written against the seeded agency (e.g., a real conversation started against the seeded properties during manual testing), which is a worse failure mode than "seed data is slightly stale until the dataset file changes."

## Dependency versions

`drizzle-kit@0.31.10` (dev dependency — CLI for `generate`/`migrate` tooling; runtime migration uses the `drizzle-orm` migrator, already a dependency) and `bcryptjs@3.0.3` (pure-JS bcrypt, avoids a native-module build step inside the Docker image) — both pinned exactly, per the brief's known-good versions for 2026-09-05.
